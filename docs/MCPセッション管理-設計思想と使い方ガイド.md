# MCP セッション管理 設計思想と使い方ガイド

## 📖 概要

TDD/DDD/Layered expert カスタムコマンド群における**MCP セッション管理**（20-22 番台）の設計思想と実用的な使用方法を解説します。

## 🧠 核心概念の理解

### セッションとは何か

```
セッション = コンテキスト + 思考 + 設計思想 の固まり
```

**具体的な構成要素**:

- **コンテキスト**: 「なぜその設計を選んだか」
- **思考**: 「どのような課題があったか」
- **設計思想**: 「何を学習したか」「どう進化したか」

### ❌ セッションではないもの

- 日次作業の区切り（毎日実行するものではない）
- 単純な作業時間の区切り
- ファイルやコードの状態管理（それは git の役割）

### ✅ セッションが管理するもの

- ドメインモデルの進化過程と判断理由
- 設計判断の背景と学習内容
- テスト戦略の変遷と経験
- 技術的負債の認識と対策の履歴

## 🔄 3 つのコマンドの役割分担

### 20-context-session-stageup: 「賢い再スタート」

```bash
/context-session-stageup /path/to/project
```

#### 実際の処理内容

```python
# 誤解されがちな動作
❌ 白紙に戻す: 現在のコンテキスト → [消去] → 空の状態

# 実際の動作
✅ 過去の蓄積を活用: 過去の記憶 + 現在の状況 → [圧縮・整理・整頓] → 強化されたコンテキスト
```

#### 「圧縮・整理・整頓」の具体例

**Before（散らばった状態）**:

```json
{
  "memory_fragments": [
    "Userエンティティはvalidation重要",
    "passwordはhash化必須",
    "JWT実装で苦労した",
    "テストでmocker使うべき",
    "Domain層は純粋に保つ"
  ]
}
```

**After（整理された状態）**:

```json
{
  "structured_knowledge": {
    "authentication_patterns": {
      "entity_design": "Userエンティティ + validation",
      "security": "password hash + JWT",
      "learned_lesson": "Domain純粋性の重要性"
    },
    "testing_strategy": {
      "tools": ["mocker"],
      "approach": "Domain-first testing"
    }
  }
}
```

### 21-checkpoint-session: 「思考の変遷記録」

```bash
/checkpoint-session milestone_name
```

#### 目的

- セッション状態の変遷を記録
- 設計判断の進化過程を保存
- 思考プロセスの変化を追跡
- 学習内容の蓄積

#### 対象範囲

```bash
✅ 含まれるもの:
- Serenaメモリ状態
- 実行履歴とメタデータ
- 設計思想と判断理由
- 学習内容と経験

❌ 含まれないもの:
- ソースコード（gitの役割）
- ファイルシステム
- データベース状態
```

### 22-recovery-session: 「思考の復元」

```bash
/recovery-session milestone_name
```

#### 目的

- 過去の時点のコンテキスト＆思想＆設計思想を復元
- 「あの時なぜそう決めたのか」を思い出す
- 設計の背景にある思考を復元

#### git ロールバックとの違い

| 側面         | git ロールバック   | recovery-session    |
| ------------ | ------------------ | ------------------- |
| **対象**     | ソースコードのみ   | 思考・設計思想      |
| **目的**     | ファイル状態復元   | コンテキスト復元    |
| **使用場面** | コードの巻き戻し   | 設計判断の想起      |
| **実行方法** | `git reset --hard` | `/recovery-session` |

#### 併用パターン

```bash
# 完全復旧したい場合
git checkout feature/auth-v1    # コード復旧
/recovery-session auth_design   # 思考復旧

# 思考だけ参照したい場合
/recovery-session design_phase_1  # コードは触らない
```

## 📅 セッションの境界と使用タイミング

### セッション開始のトリガー

1. **新しい開発スプリント開始時**
2. **長期休暇後の作業再開時**
3. **大きなマイルストーン達成後**
4. **重要な設計変更前**

### セッション終了のトリガー

1. **作業の自然な区切り**（複数 Issue 完了）
2. **設計フェーズ完了時**
3. **チェックポイント作成時**
4. **重要な学習成果達成時**

### 時間軸での区切り判断

| 時間単位           | セッション境界 | 理由                         |
| ------------------ | -------------- | ---------------------------- |
| **時間単位**       | ❌ なし        | 短すぎる                     |
| **日単位**         | ❌ なし        | 開発コンテキストが継続       |
| **週単位**         | △ 場合により   | 大きな進捗区切りの場合のみ   |
| **スプリント単位** | ✅ 適切        | 設計・実装の論理的区切り     |
| **フェーズ単位**   | ✅ 適切        | ドメイン設計 → 実装 → テスト |

## 🎯 実用的な運用例

### 運用例 1: 新機能開発

```bash
# 【セッション1】ユーザー認証機能の設計・実装（2-3週間）
/context-session-stageup
/create-use-case 101    # 認証機能
/domain-modeling 101
/create-tests 101
/checkpoint-session auth_design_complete  # 設計完了時点

# 【セッション継続】認証機能の実装継続
/implement-domain 101
/implement-usecase 101
# セッション自然終了（認証機能完了）

# 【セッション2】決済機能の設計・実装（数週間後）
/context-session-stageup  # 過去の認証設計記憶を整理・活用
/create-use-case 201    # 決済機能（認証との連携を考慮した設計が可能）
```

### 運用例 2: 設計方向転換

```bash
# 大胆な設計変更を試行
/checkpoint-session before_major_refactor

# 実験的実装
/domain-modeling-enhanced 201
# ... 実装作業 ...

# 失敗判断後の復旧
git reset --hard HEAD~10                    # コード復旧
/recovery-session before_major_refactor     # 設計思考復旧
```

### 運用例 3: チーム引き継ぎ

```bash
# 新メンバーによるプロジェクト参加
git clone ...                              # コード取得
/recovery-session team_knowledge_base      # プロジェクトの思考プロセス復元
/context-session-stageup                    # 新メンバー用コンテキスト初期化
```

## 🔧 MCP セッション管理の価値

### 1. 認知負荷軽減

- 散らばった記憶 → 整理された知識
- 断片的な学習 → 構造化されたパターン
- 重複する試行錯誤 → 効率的な判断

### 2. 継続性確保

- プロジェクト間でのノウハウ蓄積
- 設計判断の一貫性維持
- 学習内容の永続化

### 3. 品質向上

- 過去の失敗パターン回避
- ベストプラクティスの自動適用
- アンチパターンの早期発見

### 4. 意思決定支援

- データドリブンな設計判断
- 経験に基づく優先順位付け
- リスク予測と対策

## ⚠️ 重要な注意事項

### 実行頻度について

```bash
❌ 毎日実行するものではない:
毎朝9時: /context-session-stageup  # 過剰
毎夕6時: /checkpoint-session      # 無意味

✅ 論理的区切りでの実行:
スプリント開始: /context-session-stageup
重要マイルストーン: /checkpoint-session
設計方向転換前: /recovery-session
```

### 責任分離の原則

```bash
git: コードとファイルの管理
MCP Session: 思考とコンテキストの管理
```

この明確な分離により、それぞれが最適化され、相互補完的に機能します。

### 定性的効果

- **学習効率向上**: 試行錯誤の重複排除

## 🎯 まとめ

MCP セッション管理は、**コード管理（git）とは独立した思考・コンテキスト管理システム**です。

**核心価値**:

- 過去の学習を未来に活かす「賢い継続性」
- 散らばった経験を整理された知識に変換
- 設計判断の透明性と追跡可能性
- プロジェクト間での知識蓄積と活用

**運用原則**:

- 日次ではなく論理的区切りでの使用
- git との責任分離を維持
- チェックポイントは意味のある節目で作成
- リカバリーは思考の復元目的で使用

この設計思想を理解することで、TDD/DDD ワークフローにおける知識管理と継続的学習が実現され、開発効率と品質の大幅な向上が期待できます。

## 🚀 MCP 統合コマンド群の全体像（20-25 番台）

### コマンド群の構成と関係性

#### **serena の初期化**

- **serena オンボーディングを始めてください**

#### **セッション管理系（20-22 番台）**

- **20-context-session-stageup**: 賢い再スタート（コンテキスト統合）
- **21-checkpoint-session**: 思考の変遷記録（状態保存）
- **22-recovery-session**: 思考の復元（過去状態復旧）

#### **MCP 強化実行系（04-05 Enhanced 番台）**

- **04-domain-modeling-enhanced**: MCP 強化ドメインモデリング
- **05-create-tests-enhanced**: MCP 強化テスト作成

#### **分析・洞察系（25 番台）**

- **25-analytics-dashboard**: 包括的戦略分析ダッシュボード

### 🔄 既存コマンドとの併存設計

#### **Enhanced 版は置き換えではなく選択肢**

```bash
# 標準版（軽量・高速）
/domain-modeling 123      # 既存の標準的なドメインモデリング
/create-tests 123         # 既存の標準的なテスト作成

# Enhanced版（MCP強化・高機能）
/domain-modeling-enhanced 123  # MCP強化ドメインモデリング
/create-tests-enhanced 123     # MCP強化テスト作成
```

#### **使い分けの指針**

| 側面         | 標準版（04-05 番台）   | Enhanced 版（04-05 Enhanced 番台） |
| ------------ | ---------------------- | ---------------------------------- |
| **実行速度** | 高速                   | やや重い（MCP 処理）               |
| **機能**     | 基本機能               | AI 分析・推奨機能                  |
| **MCP 要件** | 不要                   | 必要                               |
| **適用場面** | シンプルなプロジェクト | 複雑・戦略的プロジェクト           |

### 📊 分析系コマンドの深化

#### **16/17 番台（基本ステータス）vs 25 番台（戦略分析）**

| 分析レベル   | 16-use-case-status / 17-project-status | 25-analytics-dashboard               |
| ------------ | -------------------------------------- | ------------------------------------ |
| **焦点**     | 現状把握（「何が」完了したか）         | 戦略洞察（「なぜ」「どう活かすか」） |
| **分析深度** | 表面的（数値・進捗率）                 | 深層的（設計思想・学習パターン）     |
| **出力**     | ステータスレポート                     | 戦略コンサルティング                 |
| **使用頻度** | 週次・日次                             | 月次・マイルストーン時               |

#### **25 番台が答える戦略的質問**

- 🧠 **なぜ**その設計判断をしたか？
- 🧠 **どのような学習**があったか？
- 🧠 **今後の戦略**は何がベストか？
- 🧠 **過去の経験**をどう活かすか？
- 🧠 **設計思想の一貫性**は保たれているか？

### 🎯 総合的な運用戦略

#### **日常運用フロー**

```bash
# 週次: 基本ステータス確認
```
