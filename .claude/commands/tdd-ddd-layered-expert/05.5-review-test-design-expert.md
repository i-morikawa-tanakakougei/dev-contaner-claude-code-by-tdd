## 🚀 専門家実行フロー

### Phase 1: TDD RED段階検証
**専門家として以下を実行:**
1. **全テスト実行・失敗状態確認**
   ```bash
   # Execute all tests to verify RED phase
   echo "Executing test suite to validate RED phase..."
   uv run --frozen pytest tests/ -v --tb=short
   
   # Expected: All tests should fail with appropriate reasons
   # Valid failure reasons: ImportError, NotImplementedError, AttributeError (missing implementation)
   # Invalid: Tests passing (indicates implementation exists) or logical errors
   ```
   
2. **テスト失敗理由の妥当性評価**
   - 確認ポイント: ImportError（未実装モジュール）、NotImplementedError（明示的未実装）による適切な失敗
   - 判断基準: 実装不在による失敗、論理エラーやテストバグによる失敗でないこと

### Phase 2: Given-When-Thenシナリオカバレッジ分析
**専門家として以下を評価:**
1. **シナリオ・テスト対応関係確認**
   ```
   カバレッジ分析項目:
   - シナリオ完全性: 全Given-When-Thenシナリオのテスト存在確認
   - 受け入れ基準対応: 各受け入れ基準に対する明示的テスト確認
   - エッジケース網羅: 境界値・例外条件のテストカバレッジ確認
   ```
   
2. **ビジネスロジックテスト品質評価**
   ```
   テスト品質評価基準:
   - ビジネス意図明確性: テスト名・構造からビジネス要求の理解可能性
   - テスト独立性: 各テストの独立実行可能性と副作用なし確認
   - データ品質: テストデータの現実性・代表性・保守容易性
   ```

### Phase 3: テスト構造・保守性品質評価
**専門家として以下を実行:**
1. **テストアーキテクチャ適合性確認**
   - アクション: レイヤーアーキテクチャ対応テスト構造確認（unit/integration/e2e分離）
   - 期待結果: 適切な抽象化レベルでのテスト実装、モック戦略の妥当性確認
   
2. **テスト保守性・拡張性評価**
   - アクション: テストコード品質評価（命名・構造・重複・依存関係）
   - 期待結果: 長期メンテナンス可能性確保、要件変更への対応容易性確認
