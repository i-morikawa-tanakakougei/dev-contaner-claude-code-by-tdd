TDD実装前にドメインモデル設計のDDD準拠性とアーキテクチャ品質をレビューする。

## メタデータ
- **前提条件**: ドメインモデル設計作成済み（04-domain-modeling）
- **入力**: イシュー番号（必須）、機能名（任意）
- **出力**: 
  - ドメイン設計レビューレポート
  - DDD準拠性分析
  - レビューステータス付き更新 `docs/use_cases/issue-X-Y.json` メタデータ
  - 設計承認または修正要求
- **依存関係**: ドメイン設計文書、既存ドメインモデル
- **実行タイミング**: ドメインモデリング後、TDDテスト作成前

## 🔍 **設計レビュー: 分析のみ**

**⚠️ 重要な注意事項:**
- **このステップは設計レビューのみ** - ドメイン設計品質を分析・評価
- **実装や変更なし** - 評価と早期問題発見に専念  
- **品質分析** - DDD準拠性、集約境界、設計決定をレビュー
- **設計レビューレポートのみ生成** - コードや設計の修正は行わない

**レビュープロセス:**
1. `04-domain-modeling` ← ドメイン設計文書作成
2. `04.5-review-domain-design` ← **【ここにいます】設計品質レビューと検証**
3. `05-create-tests` ← TDD実装開始（承認時）
4. 代替: `04-domain-modeling` に戻る ← 再設計（重大問題発見時）

**重要早期発見焦点:**
- ✅ DDD集約境界違反（イシュー#3のTrade-Position結合のような）
- ✅ エンティティ/値オブジェクト分類精度
- ✅ ビジネスルール配置とカプセル化
- ✅ 既存ドメインモデルとの統合

## よくあるエラーと解決策

### ❌ エラーケース1: DDD集約境界違反
**原因**: 集約境界を越えた直接エンティティ参照（Trade→Positionのような）  
**解決策**: 
```bash
# 集約結合を修正
- 直接オブジェクト参照を文字列ID参照に置換
- 境界を越えた整合性に協調集約を使用
- 集約間操作にドメインサービスを実装
# その後再レビュー
/review-domain-design <issue-number>
```

### ❌ エラーケース2: ドメインモデル設計文書が見つからない
**原因**: 設計作成前にドメイン設計レビューを実行  
**解決策**: 
```bash
# まずドメイン設計を作成
/domain-modeling <issue-number>
# その後レビュー実行
/review-domain-design <issue-number>
```

### ❌ エラーケース3: 既存ドメインモデルとの不整合
**原因**: 新しい設計が確立されたドメインパターンや共有基盤と競合  
**解決策**: 
- 整合性のために既存ドメインモデルを分析
- 共有値オブジェクトとパターンに整合
- 必要に応じて既存モデルのリファクタリングを検討
- アーキテクチャ一貫性を保つよう設計を更新

## タスク詳細

**🤖 エージェント統合**: このコマンドは最適なドメイン設計品質評価のために `04.5-review-domain-design` 専門エージェントを使用します。

重要なポイント:
- 集約境界設計に注目 - ここでは最も重要なDDD違反が発生する
- 確立されたドメインモデルと共有基盤との統合を検証
- ビジネスルールがドメインオブジェクトに適切にカプセル化されていることを確認
- 値オブジェクトが不変として適切に設計されていることをチェック
- エンティティ識別とライフサイクル管理が適切であることを確認
- すべてのユーザー向け出力は日本語である必要があります
