GitHubイシューからTDD/DDD/レイヤードアーキテクチャ原則に従って詳細なユースケース仕様を作成する。

## メタデータ
- **前提条件**: GitHubイシューの存在、スプリント計画（任意）
- **入力**: イシュー番号（必須）
- **出力**: 
  - ユースケース仕様: `docs/use_cases/issue-X-Y.json`
  - Given-When-Thenシナリオ
  - ドメイン概念定義
- **依存関係**: GitHub CLI（`gh`）、Git設定
- **実行タイミング**: スプリント計画後、ドメインモデリング前

## 実行例

### ✅ 成功例
```bash
$ /create-use-case 15
📖 Issue #15 のユースケース仕様作成を開始します
🔍 GitHubイシュー分析中...
✅ イシュー #15: ユーザー認証機能
🎯 Given-When-Thenシナリオ作成中...
  ✅ シナリオ1: 有効な認証情報でログイン
  ✅ シナリオ2: 無効な認証情報でログイン失敗
📝 ドキュメント作成完了: docs/use_cases/issue-15-user-auth.json
🎉 ユースケース作成完了!
```

## 📋 **ユースケース作成タスクチェックリスト**

### 🔴 必須タスク

#### **📖 GitHubイシュー分析**
- [ ] **イシュー内容分析**: GitHubイシューの要件と受け入れ基準を詳細に分析
- [ ] **ビジネス価値確認**: イシューがどのようなビジネス価値を提供するかを特定
- [ ] **ステークホルダー要件抽出**: イシューから関係者の要求を抽出
- [ ] **制約と前提条件特定**: 技術的・ビジネス的制約を明確化

#### **📋 Given-When-Thenシナリオ作成**
- [ ] **主要シナリオ作成**: 成功パスのメインシナリオをGiven-When-Then形式で記述
- [ ] **代替シナリオ作成**: 例外フローと代替パスをシナリオで記述
- [ ] **エラーシナリオ作成**: 失敗ケースと異常系のシナリオを作成
- [ ] **受け入れ基準マッピング**: イシューの受け入れ基準を各シナリオにマッピング

重要なポイント:
- GitHubイシューからGiven-When-Thenシナリオへの正確な変換
- ドメイン概念とユビキタス言語の確立
- 境界コンテキスト内での一貫性確保
- すべてのユーザー向け出力は日本語である必要があります
