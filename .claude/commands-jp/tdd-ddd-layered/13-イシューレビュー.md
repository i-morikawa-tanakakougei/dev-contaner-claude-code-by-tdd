TDD/DDD/レイヤードアーキテクチャ実装を包括的に分析してレビューする。

## メタデータ
- **前提条件**: 実装完了、全テスト成功
- **入力**: イシュー番号（必須）
- **出力**: 
  - 包括的レビューレポート
  - 品質メトリクスと分析
  - 更新された `docs/use_cases/issue-X-Y.json` メタデータ
- **依存関係**: 実装コード、テスト結果、分析ツール
- **実行タイミング**: リファクタリング後、プルリクエスト作成前

## 🔍 **品質レビュー: 分析のみ**

**⚠️ 重要な注意事項:**
- **このステップは品質レビューのみ** - 実装品質を分析・評価
- **実装変更なし** - 評価とフィードバック生成に専念  
- **品質分析**: アーキテクチャ準拠性、テストカバレッジ、コード品質を分析
- **レビューレポートのみ生成** - コード修正は行わない

**レビュープロセス:**
1. `11-refactor` ← 実装とリファクタリング完了
2. `13-review-issue` ← **【ここにいます】品質レビューと分析**
3. `14-apply-feedback` ← レビューフィードバックと改善の適用
4. `15-create-pr` ← プルリクエスト作成

## 実行例

### ✅ 成功例
```bash
$ /review-issue 15
🔍 Issues: #15 の実装レビューを開始します
📊 品質メトリクス分析中...
✅ テストカバレッジ: 92%
✅ アーキテクチャコンプライアンス: ✅
✅ コード品質: Grade A
📝 レビューレポート作成中...
✅ レビューレポート: docs/reviews/issue-15-review.md
🎉 レビュー完了 - PR作成準備完了!
```

### ❌ 失敗例と修正
```bash
$ /review-issue 15
❌ アーキテクチャ違反が検出されました
💡 違反箇所を修正してから再レビューしてください
# 修正: 違反を対処してから再レビュー
$ /review-issue 15
```

## 📋 **包括的品質レビュータスクチェックリスト**

### 🔴 必須タスク

#### **📖 Given-When-Then仕様カバレッジ分析**
- [ ] **シナリオとテストのマッピング**: 各Given-When-Thenシナリオに対応するテストがあることを確認
- [ ] **シナリオ完全性検証**: イシュー仕様からのすべてのシナリオがテストされていることを確認
- [ ] **シナリオ正確性確認**: テストが指定されたシナリオを正確に実装していることを確認
- [ ] **受け入れ基準カバレッジ評価**: すべての受け入れ基準がテスト検証されていることを確認

#### **🧪 テスト品質評価**
- [ ] **テスト構造分析**: テスト構成と命名規則をレビュー
- [ ] **テスト可読性評価**: テストがビジネス意図を明確に表現しているかを評価
- [ ] **テスト分離確認**: テストが副作用なく独立して実行されることを確認
- [ ] **アサーション品質検証**: テストが実装ではなく動作を検証していることを確認

#### **📊 テストカバレッジ分析**
- [ ] **カバレッジレポート生成**: `uv run --frozen pytest --cov=src --cov-report=html` を実行
- [ ] **ライン別カバレッジ分析**: 層ごとのコードカバレッジ割合をレビュー
- [ ] **ブランチカバレッジ評価**: ビジネスロジックの判断パスカバレッジを評価
- [ ] **カバレッジギャップ特定**: 重要な未テストコードパスを発見

重要なポイント:
- Given-When-Thenトレーサビリティに注目 - すべてのビジネスシナリオには明確なテストカバレッジが必要
- 全層のアーキテクチャ準拠性を検証
- PR進行前に包括的品質分析を確保
- 実行可能な改善推奨事項を生成
- レビュー中はコード修正ではなく分析のみに専念
- すべてのユーザー向け出力は日本語である必要があります
