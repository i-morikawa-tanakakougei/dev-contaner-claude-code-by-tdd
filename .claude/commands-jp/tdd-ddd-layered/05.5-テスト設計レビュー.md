- **出力**:

  - TDD REDフェーズ検証

- **依存関係**: テストファイル、ユースケース仕様、ドメイン設計文書
- **実行タイミング**: テスト作成後、ドメイン実装前

## 🔍 **TDDテストレビュー: 分析のみ**

**⚠️ 重要な注意事項:**
- **このステップはテストレビューのみ** - TDDテスト設計品質を分析・評価
- **実装やテスト変更なし** - 評価と検証に専念  
- **品質分析** - テストカバレッジ、シナリオマッピング、REDフェーズ準拠性をレビュー
- **テストレビューレポートのみ生成** - コードやテストの修正は行わない

**レビュープロセス:**
1. `05-create-tests` ← TDDテスト作成・失敗（REDフェーズ）
2. `05.5-review-test-design` ← **【ここにいます】テスト品質レビューと検証**
3. `06-implement-domain` ← ドメイン実装開始（承認時）
4. 代替: `05-create-tests` に戻る ← テスト修正（重大問題発見時）

**重要TDD検証焦点:**
- ✅ 全テストが適切に失敗（REDフェーズ確認）
- ✅ Given-When-Thenシナリオカバレッジ完全性
- ✅ テスト設計品質と可読性
- ✅ 適切なテスト構造と構成

## よくあるエラーと解決策

### ❌ エラーケース1: テストが成功している（REDフェーズではない）
**原因**: 偶然の実装またはテストが既存コードをテストしている  
**解決策**: 
```bash
# テストが適切に失敗することを確認
uv run --frozen pytest tests/ -v
# テストが成功している場合は、テスト実装を修正
/create-tests <issue-number>  # 適切な失敗テストを再作成
# その後再レビュー
/review-test-design <issue-number>
```

### ❌ エラーケース2: テストファイルが見つからない
**原因**: テスト作成前にテストレビューを実行  
**解決策**: 
```bash
# まずテストを作成
/create-tests <issue-number>
# その後レビュー実行
/review-test-design <issue-number>
```

### ❌ エラーケース3: Given-When-Thenカバレッジ不完全
**原因**: テストが仕様からのすべてのシナリオをカバーしていない  
**解決策**: 
- 欠落しているシナリオを分析して対応するテストを追加
- すべての受け入れ基準がテストカバーされることを確認
- ビジネスエッジケースが適切にテストされることを確認
